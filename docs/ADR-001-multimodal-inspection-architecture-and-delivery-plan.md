# ADR-001: معمارية وخطة تسليم وكيل فحص المنتجات متعدد الوسائط

- **الحالة:** معتمد للتخطيط — معلّق بدء التنفيذ على بوابات البيانات أدناه
- **التاريخ:** 2026-09-07
- **المالكون:** فريق المشروع (شخصان)
- **المراجع:** `PRD-multimodal-inspection-agent.md` و`project-discussion-summary.md`

## 1. السياق والمشكلة

المشروع الأكاديمي يحتاج نظاماً واحداً يحقق متطلبات NLP وImage Processing وDeep Learning، ثم يعرضها ضمن Agent متعدد الوسائط. يستقبل النظام نص شكوى و/أو صورة منتج، ويُنتج قراراً منظماً ومدعوماً بالأدلة.

مصدر البيانات الصورية هو MVTec AD، لكن الصور لا ترافقها شكاوى نصية حقيقية. لذلك لا يمكن تدريب Fusion متعدد الوسائط بصورة سليمة إذا دُرّب كل مسار على بيانات منفصلة ثم ادُّعي وجود تطابق بينها. كذلك حُذفت خدمات RapidAPI الخارجية من المتطلبات؛ ولا يجوز أن تصبح إجابة الوكيل معتمدة على مصادر منتجات أو أسعار على الإنترنت.

## 2. القرار

نعتمد Dataset اصطناعية **مقترنة على مستوى العينة**: لكل صورة MVTec سجل نص مولّد حتمياً/قابلاً لإعادة التوليد من فئة المنتج وحالة العيب ووسمه. يدرب النص نموذج BiLSTM متعدد المهام، وتدرب الصورة نموذج U-Net مصغراً للتقسيم، ثم تدمج تمثيلاتهما في نموذج Fusion مستقل. تنسق LangGraph هذه المكونات وتستدعي LLM فقط لصياغة التقرير من سياق مقيد بالأدلة، مع أداة محلية اختيارية لسياسات الإرجاع والضمان.

### 2.1 قرارات معمارية ملزمة

| المجال | القرار | سبب القرار | بدائل رُفضت |
|---|---|---|---|
| الصور | MVTec AD، بدءاً بفئة واحدة | ماسكات عيوب رسمية مناسبة للتقسيم والتقييم | جمع صور غير موسمة أو بدء جميع الفئات الخمس عشرة |
| الفئة الابتدائية | `bottle` كتوصية تشغيلية، ولا تصبح نهائية إلا بتأكيد الفريق | صغيرة ومفهومة وتخفض مخاطرة الوقت | `hazelnut` أو عدة فئات منذ البداية |
| النص المقترن | Templates + تنويع مضبوط + ضوضاء قابلة للضبط، مع Seed محفوظ | تطابق دلالي كامل وقابلية لإعادة الإنتاج وغطاء لمطلب Dirty Data | Dataset شكاوى مستقل أو نص مولد بلا ربط بالوسم |
| NLP | Embedding → Shared BiLSTM → رأسا `is_complaint` و`problem_type` | يحقق التصنيف الثنائي والمتعدد في نموذج واحد | RNN منفصلان أو LSTM أحادي الاتجاه |
| الرؤية | U-Net مصغر، supervised segmentation بالماسكات الرسمية | يحدد موضع العيب ويتيح IoU/Dice قابلة للشرح | CNN تصنيف فقط أو anomaly detection غير مراقب |
| Fusion | Concatenation لتمثيلي ما قبل طبقة القرار ثم Dense head | أبسط خط أساس حقيقي ويمكن قياسه | دمج نصي في Prompt فقط |
| Agent | LangGraph مع عقد حتمية للأدوات والنماذج، وLLM لصياغة الرد فقط | يحد الهلوسة ويجعل المسار قابلاً للاختبار | Agent حر يعتمد على LLM في التحليل |
| السياسات | CSV محلي عبر `policy_lookup` يستدعى فقط للاسترجاع/الاستبدال | يبرهن Tool Use بلا API خارجية | بحث ويب أو بيانات RapidAPI |

### 2.2 حدود القرار

- يمنع استدعاء APIs خارجية لبيانات المنتج أو الأسعار أو السياسات.
- ربط LLM الموجود لدى الفريق عبر OpenRouter مسموح بوصفه عقدة الصياغة النهائية، لا مصدراً لحقائق التحليل.
- دعم العربية والإنجليزية مقصور على النص المولّد في الإصدار الأول.
- واجهة العرض Demo وليست واجهة إنتاجية.
- لا يدّعي المشروع أن النصوص المولدة تمثل شكاوى عملاء حقيقية؛ بل يصرح بأنها بيانات اصطناعية مرتبطة بالصور.

## 3. عقد البيانات (Data Contract)

يُنشأ ملف `data/processed/paired_dataset.csv` من Script واحد مع `seed` ونسخة القوالب وإصدار مصدر البيانات. كل صف يمثل عينة واحدة:

| الحقل | النوع | القاعدة |
|---|---|---|
| `sample_id` | string | معرّف ثابت مشتق من مسار الصورة |
| `image_path` | string | مسار نسبي من جذر المشروع |
| `generated_text` | string | نص مطابق للوسم، قبل التنظيف |
| `is_complaint` | bool | `true` للصورة المعيبة، و`false` للصورة السليمة |
| `problem_type` | enum | `Quality`, `Packaging`, `Price`, `Delivery`, `Damage`, `Other` |
| `defect_type` | string | وسم MVTec الأصلي أو `good` |
| `severity` | enum | `Low`, `Medium`, `High` |
| `mask_path` | string/null | موجود للعيوب، و`null` للسليم |
| `split` | enum | `train`, `validation`, `test`، بلا تسرّب |
| `generator_version` | string | نسخة القوالب وقواعد الضوضاء |
| `seed` | integer | Seed المستخدم في إنتاج السجل |

### قواعد الجودة والحماية من التسرّب

1. التقسيم يتم قبل Augmentation، ولا تنتقل الصورة أو أي نسخة منها بين التقسيمات.
2. لا تستخدم عيّنات الاختبار لضبط القوالب أو hyperparameters أو قرار البنية.
3. الصورة السليمة لا تحمل قناع عيب، وتنتج نصاً غير شكوى لا شكوى عيب مصطنعة.
4. يراجع الفريق عينة عشوائية لا تقل عن 20 نصاً، ويسجل النتيجة في تقرير البيانات.
5. يراقب توزيع `problem_type`؛ لا تتجاوز فئة 50% إلا بتبرير موثق. عند عدم كفاية تنوع MVTec، يُوازن مولد النصوص بالـtemplates دون تغيير صورة أو وسمها.

## 4. مخطط التدفق التشغيلي

```text
Image + optional text
       │
       ├── Text preprocessing → BiLSTM → complaint/problem/severity + embedding
       ├── Image preprocessing → U-Net → mask/defect evidence + embedding
       └── Information extraction → Fusion → evidence context
                                                  │
                          return/exchange? ──────┼── yes → local policy CSV
                                                  │
                                                  └── LangGraph LLM → structured final report
```

لا تُمرر للـLLM إلا نتائج النماذج والحقول المنظمة والسياسة المحلية إن وجدت. عند انخفاض الثقة أو غياب modality، تظهر الحالة صراحة في التقرير ولا يُستنتج عيب أو ضمان غير موجود.

## 6. توزيع مقترح للعمل لفريق من شخصين

| المسار | العضو أ | العضو ب | نقطة الدمج |
|---|---|---|---|
| التأسيس والبيانات | إعداد مشترك | إعداد مشترك | P0 ثم P1 |
| التخصص | Text generator + NLP + extraction | Image processing + segmentation | artifacts بعقد ثابتة |
| التكامل | Fusion + Agent + UI مشتركة | Fusion + Agent + UI مشتركة | P6–P8 |
| التسليم | تقرير NLP/Agent | تقرير Vision/DL | P9 مراجعة مشتركة |

يُثبت عقد البيانات وأبعاد الـembeddings وواجهات inference قبل بدء العمل المتوازي؛ فلا تُعدّل من طرف واحد دون تحديث version واختبارات التوافق.

## 7. المخاطر والتخفيف

| الخطر | الأثر | التخفيف | مؤشر الإنذار |
|---|---|---|---|
| عدم توفر MVTec محلياً | يوقف مراحل البيانات والتدريب | لا تبدأ التدريب؛ استخدم validator بعد التنزيل | P0-S3 لا يجد الفئة |
| نصوص مكررة أو منحازة | F1 مضلل وضعف التعميم | templates متنوعة وseed ومراجعة وتقرير توزيع | تطابقات كثيرة أو فئة >50% |
| صغر البيانات | overfitting في U-Net/Fusion | augmentation للتدريب فقط، early stopping، نموذج صغير | فجوة train/validation كبيرة |
| تسرّب بين التقسيمات | نتائج غير صادقة | split أولاً وmanifest ثابت واختبارات hash/path | نفس أصل الصورة في تقسيمين |
| Fusion لا يتحسن | يفشل ادعاء G4 | تقرير النتيجة بصراحة وتحليل، لا تضخيم النتائج | delta ≤ 0 |
| هلوسة LLM | تقرير غير موثوق | context evidence-only وقواعد عدم الاختلاق وfallback منظم | ادعاء غير موجود في state |
| مفتاح/مزود LLM غير متاح | تعطل الصياغة النهائية | adapter مع رسالة fallback منظمة واختبار mock | فشل health check |

## 8. بوابات تتطلب تدخلاً من الفريق

هذه عناصر خارجية لا ينبغي للكود تخمينها:

1. **تأكيد فئة MVTec:** يوصى بـ`bottle` كبداية. يمكن اعتماد `hazelnut` بدلاً منها، لكن يلزم تثبيت قرار واحد قبل P0-S3/P1.
2. **تنزيل MVTec AD ووضع الفئة المختارة في** `data/raw/mvtec/<category>/`. بسبب حجم البيانات والترخيص، هذه خطوة يدوية من الفريق.
3. **إنشاء** `data/policies.csv` **أو اعتماد محتواه:** الحقول اللازمة هي `product_category,return_window_days,warranty_summary`. يلزم أن تكون السياسة الحقيقية/المعتمدة للمشروع، لا ينبغي اختلاقها.
4. **توفير إعداد الوصول للـLLM محلياً:** متغيرات البيئة/الإعدادات المتفق عليها لدى الفريق، من دون وضع مفاتيح في المستودع.
5. **تثبيت توزيع المسؤوليات:** المقترح في القسم 6 صالح كبداية ما لم يرغب الفريق بعكسه.

## 9. Definition of Done النهائي

- Dataset مقترنة قابلة لإعادة الإنتاج، موثقة بالـseed والإصدار ونتيجة المراجعة اليدوية.
- BiLSTM وU-Net محفوظان مع artifacts inference وتقارير القياس.
- صور معالجة قبل/بعد، ونتائج segmentation مرئية، وConfusion Matrix للنص.
- مقارنة على test split موحد بين النص والرؤية والـFusion مع تحليل صادق للنتيجة.
- LangGraph يعمل للحالات الثلاث ويستدعي CSV المحلي شرطياً، ويعرض عدم اليقين بدلاً من اختلاقه.
- Demo محلي وسيناريوهات E2E ودليل تشغيل وتقارير المواد الثلاث.

## 10. العواقب

هذا القرار يرفع موثوقية الربط بين النص والصورة ويتيح Fusion حقيقياً، لكنه يجعل نجاح التجربة مشروطاً بجودة تصميم النص الاصطناعي وشفافية توثيقه. البدء بفئة واحدة يقلل المخاطر ويمنح تسليماً قابلاً للعرض؛ التوسع إلى فئات إضافية لاحقاً يتم عبر تحديث خريطة الوسوم والقوالب والسياسات وإعادة التقييم، لا عبر تغيير المعمارية.
